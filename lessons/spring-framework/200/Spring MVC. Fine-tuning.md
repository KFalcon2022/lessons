# Spring MVC. Тонкая настройка

Это заключительная статья раздела, посвященного Spring MVC. В ней мы рассмотрим, в первую очередь, возможности, которые
предоставляет интерфейс `WebMvcConfigurer`, также затронем несколько побочных тем.

Стоит сразу сделать ремарку: кастомизация и тонкая настройка - практически бесконечно обширная тема, в зависимости 
от того, что именно и какими средствами мы собираемся настраивать. Данная статья скорее обзорная - она показывает 
ключевые интерфейсы и тезисно описывает их взаимосвязи. Также рассматривается общая структура API `WebMvcConfigurer` 
и ряд более конкретных примеров, наиболее актуальных, по мнению автора, с практической точки зрения.

Даже такой уровень погружения в кастомизацию стандартного поведения - едва ли уровень реального начинающего 
разработчика. Однако полностью опустить тему в курсе тоже нельзя - это буквально введение в будущие точки роста, 
непосредственно связанные с более глубоким погружением именно в Spring MVC (при необходимости эти же знания можно в 
значительной степени перенести на реактивный Spring WebFlux), без отвлечения на смежные разделы. 

> Статья написана на основе Spring 6.2.
> 
> В более новых версиях фреймворка, особенно в Spring 7, появляются новые отдельные механизмы, какие-то - изменяются или
> дополняются, это может быть важно для отдельных примеров. Но общий подход остается неизменным и его вполне можно
> изучать на базе текущей статьи. 

## Основные элементы API

### `WebMvcConfigurer`

`WebMvcConfigurer` - ключевой интерфейс для кастомизации `HandlerInterceptor`, `HandlerMethodArgumentResolver` и 
других инструментов, которые используются внутри логики `DispatcherServlet`.

В случае использования Spring MVC без Spring Boot, чаще всего такой интерфейс будет использоваться в качестве предка 
для класса конфигурации, аннотированного `@EnableWebMvc`:

```java
@Configuration
@EnableWebMvc
@ComponentScan("com.walking.springmvc")
public class WebConfig implements WebMvcConfigurer {
    // ... собственные методы конфигурации и переопределение методов WebMvcConfigurer
}
```

Как и в более ранних статьях, такой класс конфигурации стоит зарегистрировать в конфигурации `DispatcherServlet`:

```java
public class WebAppInitializer extends AbstractAnnotationConfigDispatcherServletInitializer {
    @Override
    protected Class<?>[] getServletConfigClasses() {
        return new Class<?>[]{WebConfig.class};
    }
    
    // ... - другие методы конфигурации
}
```

`WebAppInitializer` в данном случае будет найден механизмами контейнера сервлетов - как было описано в предыдущих 
статьях, он фактически выполняется через одного из налседников `ServletContainerInitializer`. Именно запуск 
сервлетного инициализатора и станет точкой инициализации для Spring-приложения, component scan и других шагов 
инициализации `ApplicationContext`.

С API `WebMvcConfigurer` мы познакомимся чуть позже. Пока ключевой деталью является то, что методы 
`WebMvcConfigurer` представляют собой, по сути, callback'и - методы конфигурации, которые сами по себе не создают 
ничего, однако будут вызваны реальными методами конфигурации (чаще всего в наших реалиях - `@Bean`-методами) в 
системных классах конфигурации Spring.

Цепочку от нашего собственного наследника `WebMvcConfigurer` до реальных `@Bean`-методов мы постараемся отследить в 
ближайших пунктах.

### `WebMvcConfigurerComposite`

`WebMvcConfigurerComposite` - имплементация `WebMvcConfigurer`, определенная в самом Spring MVC. Сама по себе она не 
несет полезной нагрузки. Единственная задача этого класса - получить от более высокоуровневой сущности 
(рассматриваем ниже) список всех остальных реализаций `WebMvcConfigurer` и вызвать все методы-коллбэки из каждой 
такой найденной реализации.

> С точки зрения дизайна решения - это одна из реализаций знакомого нам паттерна Composite. В Spring MVC он достаточно 
> популярен - мы уже сталкивались с `HandlerExceptionResolverComposite` с примерно той же зоной ответственности, но в 
> разрезе `HandlerExceptionResolver`, существуют и иные примеры.

Ключевым для нас здесь является то, что в приложении в принципе может быть более одной реализации `WebMvcConfigurer`,
не считая самого `WebMvcConfigurerComposite`.

Несколько реализаций `WebMvcConfigurer` может возникнуть как в самом приложении, так и за счет внешних библиотек. 
Вариант с приложением пока опустим - это скорее вопрос архитектуры и организации кодовой базы, нежели какая-то 
техническая сложность. А про собственные реализации `WebMvcConfigurer`, поставляемые в библиотеках, стоит сказать 
пару слов.

Различные инструменты - как внутри экосистемы Spring, так и вне ее (но с адаптерами для работы в Spring-приложениях) 
могут требовать собственную кастомизацию при обработке HTTP-запросов. Например:

- Swagger (a.k.a. OpenAPI). Мы шапочно знакомы с этим инструментом - он позволяет документировать HTTP API и даже 
  предоставляет простой UI с документацией запросов и возможностью эти запросы вызывать. Собственно, для отображения 
  генерируемых им HTTP-страниц (фактически, статических элементов), ему требуется собственный обработчик для статики.
  В зависимости от используемой библиотеки, Swagger может регистрировать такой обработчик через `WebMvcConfigurer`;
- Spring Data и Querydsl - набор библиотек для работы с БД. В норме взаимодействие с БД и соответствующие 
  библиотеки не должны в принципе влиять на слой HTTP-коммуникации. Но на практике появляются дополнительные удобные 
  аннотации или иные второстепенные факторы, которые приводят к потребности в новых реализациях 
  `HandlerMethodArgumentResolver`, форматтеров или иных сущностей, которые требуется зарегистрировать;
- Кастомизации в Spring Boot. С ними чуть сложнее, но как минимум механизм автоконфигурации использует собственную 
  реализацию `WebMvcConfigurer`.

Подводя итог, `WebMvcConfigurer` - просто инструмент. Который может быть полезен как непосредственно коду приложения,
так и библиотекам, имеющим интеграцию со Spring MVC. Как закономерный итог - в приложении может существовать целый 
список реализаций `WebMvcConfigurer`, которые необходимо свести воедино. Чем и занимается рассматриваемый 
`WebMvcConfigurerComposite`.

Практический нюанс - внутри списка все реализации ранжируются на основании `@Order`. Чаще всего порядок не критичен, 
но если ваша реализация как-то использует классы внешних библиотек или перетирает, а не расширяет, конфигурацию 
(такие возможности тоже есть) - лучше перепроверить, какие `WebMvcConfigurer` в принципе есть в вашем приложении.

### `WebMvcConfigurationSupport`

`WebMvcConfigurationSupport` - это класс конфигурации*, API которого можно разделить на две категории.

> *Класс конфигурации в широком смысле, но не с точки зрения Spring. Чуть ниже этот момент будет прояснен.

Первая из них - `@Bean`-методы. Именно в этом классе регистрируются:

- Бины-реализации `HandlerAdapter`, включая `RequestMappingHandlerAdapter`, который обрабатывает методы контроллеров;
- Реализации `HandlerMapping`;
- Бин `HandlerExceptionResolver` (фактически - `HandlerExceptionResolverComposite`);
- `ViewResolver` (тоже через реализацию паттерна Composite);
- Ряд других бинов, необходимых для корректной работы `DispatcherServlet`.

Вторая же часть API представлена в виде protected методов-коллбэков. По сигнатуре они сильно напоминают методы, 
которые можно увидеть в `WebMvcConfigurer`, хоть по факту эти сущности и не состоят в общей иерархии. 

Суть коллбэков - их можно переопределить в наследнике `WebMvcConfigurationSupport`, а вызовы этих коллбэков - часть 
логики `@Bean`-методов, упомянутых выше.

Таким образом получается, что `WebMvcConfigurationSupport` берет на себя базовую конфигурацию ключевых бинов, 
обеспечивающих работу `DispatcherServlet`. Одновременно с этим он предоставляет удобный API для конфигурации этих 
бинов через коллбэк методы. Так, например, `@Bean`-метод для создания `RequestMappingHandlerAdapter` вызывает 
коллбэки для конфигурации:

- Списка `HttpMessageConverter`;
- Списка `HandlerMethodArgumentResolver`;
- Списка `HandlerMethodReturnValueHandler`;
- Ряда других компонентов `RequestMappingHandlerAdapter`, с которыми мы в меньшей степени сталкивались в рамках курса.

Для большинства других `@Bean`-методов ситуация аналогична - они вызывают коллбэки, необходимые для конфигурации и 
кастомизации той или иной сущности.

> **!NB**: В отдельных случаях может потребоваться отказ от работы с `WebMvcConfigurer` и прямое наследование от 
> `WebMvcConfigurationSupport`. В первую очередь, если требуется действительно специфичная настройка - например, 
> необходимость зарегистрировать собственные реализации для `@Bean`-методов, заявленных в предке.
> 
> Такой подход может сломать множество вспомогательных механизмов, в том числе в части взаимодействия со Spring Boot 
> или иными модулями Spring Framework, но в каких-то исключительных ситуациях имеет право на жизнь. Но вероятность 
> встретиться с этим в коммерческом проекте стремится к нулю, поэтому достаточно понимать, что такая возможность 
> технически присутствует, углубляться в это не имеет особого смысла.

### `DelegatingWebMvcConfiguration`

Класс `DelegatingWebMvcConfiguration` - сердце всего механизма конфигурации, объединяющее сущности, рассмотренные выше. 

Рассмотренный выше `WebMvcConfigurationSupport` содержит в себе `@Bean`-методы. Однако сам этот класс не аннотирован 
ни как конфигурация, ни как компонент в принципе. То есть сам по себе он не будет зарегистрирован как бин.

`DelegatingWebMvcConfiguration`, в свою очередь:

- Является наследником `WebMvcConfigurationSupport`, а значит - наследует, в том числе, и `@Bean`-методы предка;
- Аннотирован `@Configuration`. Из-за этого `@Bean`-методы регистрируются в `ApplicationContext` и фактически 
  создают бины, упомянутые в предыдущем пункте статьи;
- Создает `WebMvcConfigurerComposite` (не является бином), внедряет бины, реализующие `WebMvcConfigurer` и передает 
  их в созданный объект `WebMvcConfigurerComposite`;
- Переопределяет коллбэк-методы `WebMvcConfigurationSupport`. Логика методов сводится к вызову соответствующих 
  методов-коллбэков `WebMvcConfigurerComposite`.

В результате общая схема регистрации вспомогательных бинов для `DispatcherServlet` выглядит следующим образом:

1. На основании класса-конфигурации `DelegatingWebMvcConfiguration` вызываются `@Bean`-методы, определенные в его 
   предке - `WebMvcConfigurationSupport`;
2. В логике работы указанных `@Bean`-методов есть обращения к методам-коллбэкам. На основе базового механизма 
   полиморфизма в Java используется реализация этих методов, описанная именно в `DelegatingWebMvcConfiguration`;
3. Каждый коллбэк-метод вызывает соответствующий метод `WebMvcConfigurerComposite`. Например, 
   `DelegatingWebMvcConfiguration#addInterceptors()` -> `WebMvcConfigurerComposite#addInterceptors()`;
4. Внутри логики метода-коллбэка в `WebMvcConfigurerComposite`, происходит перебор всех реализаций 
   `WebMvcConfigurer`, зарегистрированных как бины, с вызовом уже их реализации коллбэка: 
   `WebMvcConfigurerComposite#addInterceptors()` -> `WebMvcConfigurer#addInterceptors()` (для каждой реализации).

В результате финальный бин, формируемый на основе `@Bean`-метода из `WebMvcConfigurationSupport`, получает все 
необходимые ему вспомогательные элементы, заданные в пользовательских (или библиотечных) реализациях 
`WebMvcConfigurer`, зарегистрированных в качестве бинов.

Именно на базе использования `DelegatingWebMvcConfiguration` работает конфигурация абсолютного большинства Spring 
MVC приложений, включая все примеры из предыдущих статей. Если же в приложении нет ни одной реализации 
`WebMvcConfigurer` - все коллбэки, фактически, ничего не привносят и получается базовая конфигурация Spring MVC без 
каких-либо кастомных обработчиков, интерцепторов и резолверов.

### `@EnableWebMvc`

Вишенка на торте - `@EnableWebMvc`.

По сути, эта аннотация делает ровно одну вещь: импорт `DelegatingWebMvcConfiguration`, который мы разобрали выше.

Такая аннотация должна быть ровно одна на приложение. Если ее нет - `DelegatingWebMvcConfiguration` сам по 
себе просто не попадет в контекст и не произойдет магии, описанной в предыдущем пункте.

Если в вашем приложении одна собственная реализация `WebMvcConfigurer` - обычно такая реализация будет аннотирована 
`@Configuration` + `@EnableWebMvc`, как показано в примере из начала статьи.  

> В Spring Boot приложениях использовать `@EnableWebMvc` не нужно. Там собственные механизмы автоконфигурации, 
> которые данная аннотация способна сломать.

## API `WebMvcConfigurer`

Рассмотрим, какие методы предоставляет `WebMvcConfigurer`. Полный обзор делать не будем - исходники и документация к 
классу справятся с этим лучше. Но наиболее важные моменты необходимо подчеркнуть.

В первую очередь, стоит разделить методы `WebMvcConfigurer` на несколько групп:

- `add*()`/`extend*()`. Дополняют существующую конфигурацию: добавляют новые форматтеры, интерцепторы, конвертеры 
  или иные элементы, в зависимости от метода. Для таких методов порядок выполнения `WebMvcConfigurer`, в которых они 
  определены, важен только с позиции того, в каком порядке конечные элементы будут зарегистрированы в конфигурации. 
  Иногда это имеет значение, но в большинстве случаев - нет;
- `configure*()`. Такие методы замещают дефолтную конфигурацию собственной. Вся конфигурация элемента (-ов) по 
  умолчанию игнорируется в пользу заявленной через такие методы `WebMvcConfigurer`. В каких-то случаях `configure*()`
  метод является единственным способом настроить конкретный элемент (например, работа с асинхронными запросами через
  `configureAsyncSupport()`), в других - `configure*()` метод будет соседствовать с `extend*()` методом для этого же 
  элемента (скажем, `configureMessageConverters()` и `extendMessageConverters()`). Это сделано не случайно и имеет смысл
  в отдельных случаях, но в большинстве задач `add*()`/`extend*()` методы будут предпочтительны относительно
  `configure*()`;
- `get*()`. Такие методы явно указывают, что реализация метода должна быть не более чем в одном `WebMvcConfigurer` на
  `DispatcherServlet`. Если один и тот же `get*()` метод в нескольких реализациях `WebMvcConfigurer` вернет значение,
  отличное от `null` - приложение выбросит `IllegalStateException` при инициализации контекста.

Ниже представлен частичный список методов `WebMvcConfigurer`, которые, по мнению автора, наиболее часто требуются в 
прикладной разработке. Некоторые из них более детально рассмотрены в примерах:

- `addFormatters(FormatterRegistry registry)`. Позволяет регистрировать свои форматтеры, конвертеры*, парсеры. Чаще 
  всего речь идет о конвертации строкового значения в значение иного типа - числового, даты и времени, элемента енама и 
  т.д.;
- `addInterceptors(InterceptorRegistry registry)`. Позволяет добавлять собственные перехватчики. Это основной 
  механизм регистрации `HandlerInterceptor`, рассмотренных в статье о `DispatcherServlet`; 
- `addResourceHandlers(ResourceHandlerRegistry registry)`. Позволяет добавлять обработчики ресурсов. Основное 
  назначение - обработка запросов к статике, где не требуется контроллер, а необходимо лишь отдать данные, лежащие 
  по определенному пути;
- `addCorsMappings(CorsRegistry registry)`. Одна из возможных точек настройки CORS. Позволяет настраивать на 
  стороне сервера допустимость (и недопустимость) кросс-запросов от различных источников. Подробнее рассмотрим в 
  пункте, посвященном CORS; 
- `addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers)`. Позволяет регистрировать собственные argument 
  resolver'ы. Обычно - через создание и обработку собственных аннотаций, если `@RequestParam`, `@RequestHeader` и 
  иных подобных оказывается недостаточно;
- `extendMessageConverters(List<HttpMessageConverter<?>> converters)`. Позволяет добавлять собственные конвертеры 
  для тела запроса/ответа. На практике может быть актуально как для добавления новых конвертеров, так и для 
  изменения существующих - передаваемый параметром список фактически является списком всех уже зарегистрированных к 
  этому моменту конвертеров и из него можно что-либо удалять с тем же успехом, что и добавлять;
- `configureMessageConverters(List<HttpMessageConverter<?>> converters)`. Этот метод аналогичен предыдущему, за тем 
  исключением, что добавление конвертеров в этом списке отключает автоматическую регистрацию конвертеров по 
  умолчанию (актуальный список конвертеров по умолчанию можно найти в 
  `WebMvcConfigurationSupport#addDefaultHttpMessageConverters()`);
- `getValidator()`. Позволяет указать, какой валидатор должен использоваться Spring MVC для валидации запросов. 
  Может не совпадать с бином валидатора, использующимся в других компонентах Spring - отчасти это было 
  продемонстрировано в статье, посвященной валидации в Spring MVC.

> *Именно в данном контексте - используются для параметров метода контроллера, не обрабатываемых через
> `HttpMessageConverter`. То есть для тела запроса или ответа эти конвертеры не актуальны, но используются для 
> конвертации значений `@RequestParam`, `@PathVariable` и ряда других параметров метода контроллера. 

Методы, не перечисленные выше, все еще актуальны для своей специфики. Однако какие-то из них касаются классического 
Spring MVC, другие - кастомизируют поведение, которое чаще всего не изменяется относительно стандартных настроек.

## Конфигурация CORS

В течение курса мы уже несколько раз так или иначе сталкивались с CORS - в основном в качестве теоретической зоны 
применения тех или иных инструментов.

На практике, CORS обычно становится зоной ответственности Spring Security - этот модуль позволяет как расположить
описание CORS-политики рядом с конфигурацией других инструментов защиты от стандартных уязвимостей, так и перенести 
саму логику обработки CORS на более ранний этап обработки запроса, сокращая избыточные шаги по обработке в негативном 
сценарии.

Но поскольку Spring MVC имеет встроенные инструменты для тех же целей - кажется разумным и разобраться с самим 
термином, и посмотреть, как можно настраивать CORS без Security-модуля. Хотя бы чтобы потом было с чем сравнивать.

### Теория

Начать придется издалека. В Интернете сложился ряд правил для веб-сайтов, которые направлены на безопасность 
использования. Какие-то из них - лишь декларируются, другие - вшиваются внутрь браузеров (как, например, Cookies и 
ограничения браузеров по доступу к ним), третьи требуют и доработок и на клиенте, и на сервере.

Одно из таких правил - **Same-Origin Policy** (**SOP**). В максимально простом описании эта политика декларирует, 
что веб-страница (фактически - хостящий ее веб-сервер), с которой отправляется запрос к серверу, и сам сервер должны 
иметь общий протокол взаимодействия, хост и порт. То есть если мой сайт доступен по адресу `https://mysite.com`, 
JavaScript в нем должен слать запросы только к серверу `https://mysite.com`, но ни в коем случае не к 
`http://anothersite.com` или куда-либо еще. Даже к `http://mysite.com` обращаться нельзя, потому что HTTP и HTTPS - 
разные протоколы. Фактически такие кросс-запросы даже могут быть отправлены, но в таком случае браузер должен 
ограничить чтение их ответов. 

Это базовая политика, которую поддерживают все современные браузеры. Однако в ультимативном виде она не применима в 
современных веб-приложениях - веб-серверы, раздающие фронтенд-приложения и серверы, хостящие бэкенд, уже давно 
разъехались. Да и сами по себе кросс-запросы бывают необходимы в различных контекстах - от сбора аналитики и 
мониторинга ошибок до специфических систем, почему-то работающих сразу с несколькими серверами. В отдельных случаях 
все можно замаскировать под один хост определенной организацией сетевой инфраструктуры, но не всегда.

Впрочем, текущая статья посвящена не информационной безопасности, поэтому вернемся к основной теме.

Кросс-запросы важны, кросс-запросы нужны. Поэтому одним из шагов в развитии веб-технологий стал **CORS** -
**Cross-Origin Resource Sharing**. Механизм, который провозглашает: черт с вами, вот вам исключение из SOP. Но 
давайте хотя бы сервер будет валидировать, хочет он обрабатывать ваш кросс-запрос или нет.

Как CORS работает с точки зрения браузера и HTTP:

1. Если браузер видит, что JS хочет отправить HTTP-запрос, запускается проверка: протокол, хост и порт запроса тот 
   же, что у текущей страницы или нет? Поскольку текущую страницу сам браузер ранее и запросил, текущие значения он 
   знает, а целевые для запроса - указаны в самом запросе;
2. Если данные совпадают, браузер позволяет отправить запрос без каких-либо нюансов;
3. Если же хотя бы один из трех параметров различен - включается механизм CORS. Браузер автоматически добавляет в 
   запрос заголовок `Origin`, с указанием протокола, хоста и порта, с которыми была загружена текущая страница, и 
   именно в таком виде запрос уходит к целевому серверу;
4. Сервер получает запрос и считывает наличие заголовка `Origin`. Дальше возможны несколько вариантов:
   1. Браузер сначала отправил `OPTIONS`-запрос* (он же preflight-запрос) с уточнением доступа. Если CORS-политики не 
      настроены или `Origin` содержит недопустимое значение - сервер вернет клиенту ошибку (`403`) и на этом все 
      закончится;
   2. Браузер сразу отправил фактический запрос без предварительного `OPTIONS`. Здесь поведение может отличаться 
      в зависимости от технологического стека, в случае Spring MVC - сервер все равно проведет явную проверку 
      CORS-политики и, если `Origin` недопустим, вернет `403`;
   3. С preflight или без, но `Origin` допустимый - сервер обрабатывает запрос, формирует ответ и добавляет 
      заголовок ответа - `Access-Control-Allow-Origin`, в значении - адрес из `Origin` либо `*`, если сервер готов 
      обрабатывать запросы из любых источников.

> *Отправлять или не отправлять `OPTIONS` перед целевым запросом - зона ответственности браузера. Без preflight 
> отправляются запросы лишь с определенными HTTP-методами и лишь с определенным содержимым. Частный, но не единственный 
> случай такой ситуации - HTML-формы.

Объяснение выше - "на пальцах", оно несколько упрощено относительно реального положения дел. Но позволяет понять 
саму суть механизма и, главное, зону ответственности сервера.

### CORS в Spring MVC

Собственно, задача сервера - хранить на своей стороне набор допустимых значений `Origin` и, при необходимости, 
отсекать preflight-запросы или же обрабатывать целевые запросы, но управлять заголовком ответа 
`Access-Control-Allow-Origin`. Все это достаточно базовые вещи, по умолчанию вшитые в Spring MVC (см. `CorsProcessor`,
`AbstractHandlerMapping.CorsInterceptor`). Задача разработчика приложения сводится в первую очередь к описанию самой 
CORS-политики - кому позволены кросс-запросы, кому - нет.

Spring MVC предоставляет для этих целей как минимум два инструмента. Первый из них - 
`WebMvcConfigurer#addCorsMappings()`:

```java
@Configuration
@EnableWebMvc
@ComponentScan("com.walking.springmvc")
public class WebConfig implements WebMvcConfigurer {
    // Глобальная конфигурация CORS-политики для DispatcherServlet
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        // CORS-политика может быть зависима как минимум от конкретных маппингов пути и методов HTTP. Кроме того, 
        // может быть определенная привязка к авторизации и каким-либо вспомогательным заголовкам.
        registry.addMapping("/my/controller/new/**")
            // Привязка к конкретным методам HTTP. Опциональна.
            // Если не указана - допустимы строго методы GET, HEAD и POST 
            .allowedMethods("POST", "PUT", "GET")
            // Если какое-то из заданных значений совпадает со значением в заголовке Origin - оно же будет указано в
            // Access-Control-Allow-Origin
            .allowedOrigins("https://mysite.com", "https://myanothersite.com");
        // Чем более общие паттерны используются, тем позже стоит располагать их в общем списке. Так 
        // как поиск всегда идет до первого совпадения. И, скажем, паттерн "/**" соответствует вообще любому запросу.
        registry.addMapping("/**")
            // Разрешить все методы
            .allowedMethods("*")
            // Разрешить доступ с любых адресов
            .allowedOrigins("*")
            // Настройка, как долго клиент может кэшировать результат preflight-запроса. Значение задается в 
            // секундах. Здесь - 10 часов, по умолчанию - 30 минут (1800 секунд). Однако слишком большие значения не 
            // всегда имеют смысл, поскольку кроме настройки из ответа, браузер также руководствуется собственными 
            // лимитами. Они отличаются у разных браузеров, но редко превышают сутки
            .maxAge(36000);
    }

    // ... - Другие методы WebConfig
}
```

Кроме использованных выше методов есть и ряд других, менее популярных настроек, привязанных к CORS. Детали можно 
посмотреть в документации к `CorsRegistration`.

`WebMvcConfigurer#addCorsMappings()` позволяет описать глобальную конфигурацию для CORS. Кроме этого, Spring MVC 
позволяет описывать (или расширять глобальную) конфигурацию на уровне контроллера и даже метода контроллера:

```java
@RestController
@RequestMapping("/my/controller")
// Фактически атрибуты @CrossOrigin повторяют по смыслу методы CorsRegistration.
// Паттерн пути при этом вычисляется из @RequestMapping
@CrossOrigin(origins = {"https://mysite.com", "https://myanothersite.com"}, maxAge = 3600)
public class MyController {
    @GetMapping
    @CrossOrigin(maxAge = 1800)
    public ResponseEntity<?> get() {
        // ... - Реализация метода контроллера
    }

    // ... - Другие методы контроллера
}
```

> На практике аннотация не популярна. В принципе, приложение редко имеет настолько разветвленную CORS-политику, чтобы 
> варьировать ее на уровне отдельных контроллеров или, тем более, методов контроллеров. Чаще можно увидеть либо общую 
> конфигурацию на `DispatcherServlet` (что в современных реалиях почти всегда будет идентично одной конфигурации на 
> все приложение), либо несколько конфигураций для семантически разных API: скажем, отдельно `/public/**`, отдельно -
> `/admin/**`.

В конечном итоге `@CrossOrigin` объединится и между объявлениями уровней метода и контроллера, и с конфигурацией из 
`WebMvcConfigurer`. Поэтому на этапе фактической проверки запроса будет использоваться объединенная конфигурация, 
учитывающая различные источники формирования политик. Но если этот подход используется - в глобальных настройках 
стоит избегать широких паттернов вроде `/**` - они фактически поглотят более тонкие настройки.

Тем не менее в прикладной разработке что `@CrossOrigin`, что `WebMvcConfigurer#addCorsMappings()` обычно не 
используются явно, настройка CORS-политик происходит через Spring Security. Технически, можно даже совмещать оба 
подхода в одном приложении, но смысла в этом обычно нет.

## Примеры

Приведенный ниже набор примеров - утрированная демонстрация возможностей `WebMvcConfigurer`, которые так или иначе 
пригодились автору в коммерческой разработке. Ни об одном из этих примеров нельзя сказать, что это что-то, строго 
необходимое каждому проекту. Но по мере накопления опыта и специфических задач, так или иначе приходится 
кастомизировать стандартное поведение - где-то, потому что иначе нельзя, где-то - потому что вариант без 
кастомизации требует слишком много boilerplate в различных частях приложения. 

### Конвертация значения в элемент enum'а по значению поля enum 

Данный пример актуален в первую очередь для не самых новых проектов с историческими костылями.

Предположим, что когда-то у нас были эндпоинты, ожидающие на вход целочисленный параметр с определенным набором 
допустимых значений:

```java
@RestController
@RequestMapping("/users")
public class UserController {
    /**
     * @param roleId - acceptable values: 0 (guest), 1 (user) and 2 (admin) 
     */
    @PutMapping("{userId}/role/assign")
    public ResponseEntity<?> assignRole(@PathVariable Long userId, @RequestParam int roleId) {
        if (!Set.of(0, 1, 2).contains(roleId)) {
            // Для упрощения используем RuntimeException, а не полноценную ошибку валидации
            throw new RuntimeException("Incorrect role id: %s".formatted(roleId));
        }
        
        // ... - Реализация метода контроллера
    }
    
    // ... - Другие методы контроллера, в том числе с использованием roleId и его повсеместной валидацией
}
```

Со временем кому-то пришла в голову светлая мысль: раз перечень значений конечен - почему бы не создать enum?

```java
public enum Role {
    USER(1),
    ADMINISTRATOR(2),
    GUEST(0);
    
    private final int legacyRoleId;
    
    Role(int legacyRoleId) {
        this.legacyRoleId = legacyRoleId;
    }
    
    public static Role getById(int legacyRoleId) {
        return Stream.of(values())
            .filter(role -> role.legacyRoleId == legacyRoleId)
            .findFirst()
            .orElseThrow(() -> new RuntimeException("Incorrect role id: %s".formatted(legacyRoleId)));
    }
}
```

Но API изменить не разрешили в угоду обратной совместимости. Как результат - лучше стало, но не сильно:

```java
@RestController
@RequestMapping("/users")
public class UserController {
    /**
     * @param roleId - acceptable values: 0 (guest), 1 (user) and 2 (admin) 
     */
    @PutMapping("{userId}/role/assign")
    public ResponseEntity<?> assignRole(@PathVariable Long userId, @RequestParam int roleId) {
        Role role = Role.getById(roleId);

        // ... - Реализация метода контроллера
    }

    // ... - Другие методы контроллера, в том числе с использованием roleId и его повсеместной конвертацией в Role
}
```

Что мы можем сделать? Правильно, создать собственный конвертер, который будет из идентификатора роли создавать 
целевое значение:

```java
@Component
public class RoleRequestParamConverter implements Converter<String, Role> {
    @Override
    // Любые параметры запроса изначально - строки. int, который мы видим в контроллере - уже результат конвертации 
    // String -> int
    public Role convert(String source) {
        // Можно либо адаптировать поле енама и getById() для строк, или перегрузить сам метод, или парсить int прямо в 
        // конвертере. Последний вариант в прикладном коде выглядит странно, но в качестве примера более очевидно, чем 
        // остальные варианты 
        return Role.getById(Integer.parseInt(source));
    }
}

@Configuration
@EnableWebMvc
@ComponentScan("com.walking.springmvc")
public class WebConfig implements WebMvcConfigurer {
    private final RoleRequestParamConverter roleRequestParamConverter;

    // ... - Конструктор и другие методы WebConfig

    @Override
    // FormatterRegistry применяется для регистрации реализаций целой плеяды интерфейсов:
    // Converter, Formatter, Printer и Parser. Однако рассматривать все из них не имеет особого смысла
    public void addFormatters(FormatterRegistry registry) {
        registry.addConverter(roleRequestParamConverter);
    }
}
```

Теперь контроллер выглядит так:

```java
@RestController
@RequestMapping("/users")
public class UserController {
    @PutMapping("{userId}/role/assign")
    public ResponseEntity<?> assignRole(@PathVariable Long userId, @RequestParam("roleId") Role role) {        
        // ... - Реализация метода контроллера
    }
    
    // ... - Другие методы контроллера
}
```

В целом, Spring MVC поддерживает конвертацию строкового значения в элемент енама из коробки - при условии, что 
строковый литерал полностью соответствует ключу. Однако для отдельных ситуаций, вроде описанной выше, пример вполне 
имеет право на жизнь. На месте целочисленного идентификатора могло оказаться строковое значение, отличающееся от 
элемента енама по историческим причинам, или расхождение строковых значений по регистру, или еще какая-то мелкая, но 
неприятная проблема. Если это не единичный эндпоинт и проблема идет красной нитью через значимую часть API - 
использование кастомного конвертера вполне оправдано.

> Разные команды на этот вопрос могут смотреть по-разному. Кто-то предпочитает в принципе конвертацию строки в 
> элемент енама делать вручную (и у этого есть свои плюсы), кто-то по иным причинам не согласен на подобные костыли. 
> Однако наша задача на данном этапе - оценить функциональные возможности, а внутренние договоренности команд - личное 
> дело самих команд.

### `HttpMessageConverter` для JSON с собственным `ObjectMapper`

Если в проекте подключен Jackson или иная подходящая библиотека* для сериализации JSON, Spring MVC
(`WebMvcConfigurationSupport`) предоставляет реализацию `HttpMessageConverter` с использованием такой библиотеки.

> *Кроме Jackson `WebMvcConfigurationSupport` автоматически проверяет наличие зависимостей Jakarta JSON Binding API 
> и Gson. Какая библиотека есть - под ту и создает JSON-конвертер.

В бэкенд-разработке Jackson - фактически стандарт, поэтому наш пример использует его. Однако аналогичное несложно 
сделать для любой иной реализации.

Собственно, в чем проблематика примера? Spring MVC предоставляет конвертер для JSON, в нашем случае 
`MappingJackson2HttpMessageConverter`. Но для этого конвертера необходим объект `ObjectMapper`, который будет создан 
прямо на месте. При этом в приложении уже может быть собственный объект `ObjectMapper` - с дополнительными модулями 
и настройками. Такой объект может даже быть зарегистрирован как отдельный бин, но `WebMvcConfigurationSupport` все 
равно будет использовать собственноручно созданный объект.

Как результат - правила (де-) сериализации тела запроса (ответа) могут не соответствовать ожиданиям. Очевидное 
решение - зарегистрировать свой объект `MappingJackson2HttpMessageConverter` вместо предоставляемого по умолчанию:

```java
@Configuration
public class AppConfiguration {
    @Bean
    public ObjectMapper objectMapper() {
        // ... - Конфигурация и создание объекта ObjectMapper со всеми необходимыми модулями и кастомизациями
    }
}

@Configuration
@EnableWebMvc
@ComponentScan("com.walking.springmvc")
public class WebConfig implements WebMvcConfigurer {
    private final ObjectMapper objectMapper;

    // ... - Конструктор и другие методы WebConfig

    @Override
    // При использовании extendMessageConverters() дефолтные конвертеры добавляются до обработки коллбэка. 
    // Соответственно, в списке конвертеров дефолтные уже доступны.  
    public void extendMessageConverters(List<HttpMessageConverter<?>> converters) {
        // Мы знаем интересующий нас тип дефолтного конвертера. Удаляем такой конвертер из списка по условию
        converters.removeIf(converter -> converter instanceof MappingJackson2HttpMessageConverter);
        // Регистрируем собственный конвертер того же типа, но с указанием своего ObjectMapper.
        // Упрощение примера: здесь мы не переживаем о порядке конвертера, размещая новый в самом конце списка.
        // На практике это может сыграть злую шутку 
        converters.add(new MappingJackson2HttpMessageConverter(objectMapper));
    }
}
```

Альтернативой предложенному решению может быть использование `configureMessageConverters()` вместо 
`extendMessageConverters()`. При использовании `configureMessageConverters()` с фактическим добавлением конвертеров, 
реализации по умолчанию вообще не будут добавлены в конечный список `HttpMessageConverter`. Однако этот подход стоит 
использовать крайне осторожно (чаще - не нужно использовать вовсе), поскольку он предполагает отсутствие не только 
стандартного `HttpMessageConverter` для JSON, но и отсутствие всех остальных конвертеров - включая конвертеры для 
`byte[]`, строк и прочих типов, которые вполне могут пригодиться отдельным эндпоинтам приложения.

> Стоит оставить две ремарки:
>
> 1. Пример отчасти теряет актуальность в Spring 7. В этой версии произошел переход на Jackson 3, который
>    предоставляет новый API для работы с библиотекой. Сама проблематика и идея никуда не исчезают, но классы будут
>    отличаться от используемых в более ранних версиях Spring;
> 2. В Spring Boot приложениях этот пример тоже не актуален - если в таком приложении есть бин типа `ObjectMapper`,
>    он автоматически будет использоваться для соответствующего `HttpMessageConverter`. С этим тоже есть свои нюансы,
>    но они находятся за пределами данного примера.
>
> Как результат - данный пример имеет скорее учебную, чем прикладную, направленность.

#### `Jackson2ObjectMapperBuilder`

Дополнительно стоит сказать пару слов о конфигурации собственного `ObjectMapper`. Мы уже неоднократно сталкивались с 
этим типом и несколько раз конфигурировали его в практических задачах через API самого FasterXML Jackson - в 
основном с целью добавления поддержки `java.time`.

Однако Spring предоставляет собственный инструмент для настройки `ObjectMapper` - `Jackson2ObjectMapperBuilder`. Его 
ключевое преимущество заключается в возможности подложить в билдер `ApplicationContext`. Если опустить нюансы 
абстракций, это позволяет использовать преимущества Spring DI для классов, которые указаны в атрибутах вроде `using()`
аннотаций `@JsonSerialize`, `@JsonDeserialize` и некоторых других.

Для небольших проектов эта фича обычно не требуется. Но для крупных многомодульных систем, различные части которых 
могут иметь сложную логику (де-) сериализации - может быть полезно.

Стоит держать в голове, что DI в сериализаторах почти всегда избыточен просто в силу специфики самой задачи 
сериализации - если он вам требуется, возможно, вы пытаетесь завернуть в него слишком много логики. Но если ситуация 
вынуждает - решение уже придумали за вас:)

### Собственные аннотации

Периодически бывает необходимо в различных эндпоинтах получать одни и те же метаданные - значение какого-то 
специфического заголовка, параметра или чего-либо еще. Наиболее хрестоматийный пример - получение IP-адреса. 
Попробуем создать собственный `HandlerMethodArgumentResolver`, позволяющий получать IP-адрес, с которого был 
отправлен запрос, в строковом виде.

При желании - можно доработать с помощью собственного конвертера и вместо строки использовать отдельный тип для IP. 
Но мы пойдем простым путем.

```java
// Создаем собственную аннотацию для параметров метода контроллера - именно по ней будет определяться нужный резолвер
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface Ip {
}

// Создаем собственный HandlerMethodArgumentResolver. Чтобы не создавать объект по месту регистрации - объявляем 
// компонентом. Технически это не обязательно
@Component
public class IpMethodArgumentResolver implements HandlerMethodArgumentResolver {
    // Как и во многих иных подобных инструментах, нам необходимо описать, как Spring должен понять, что именно этот 
    // резолвер подходит в конкретной ситуации. Завязываем на использование ранее созданной аннотации
    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.hasParameterAnnotation(Ip.class);
    }

    // Описываем само получение адреса
    @Override
    public Object resolveArgument(MethodParameter parameter, ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest, WebDataBinderFactory binderFactory) {
        // Ранее мы тезисно затрагивали тип NativeWebRequest. Это Spring-обертка над реальным объектом запроса. В ее 
        // собственном API нет необходимого нам метода, поэтому извлекаем объект сервлетного запроса
        var request = webRequest.getNativeRequest(HttpServletRequest.class);
        
        // Самый простой способ получить адрес, с которого сделан запрос - метод getRemoteAddr().
        // Проблема в том, что современная IT-инфраструктура почти всегда предусматривает использование 
        // proxy-серверов в том или ином виде. Как результат - с этим подходом мы рискуем получить адрес 
        // промежуточного сервера, а не фактический IP-адрес клиента. Однако для корректной реализации получения 
        // IP-адреса с учетом промежуточных серверов необходимо знать детали конфигурации, поэтому в примере 
        // ограничимся лишь примитивным решением
        return request.getRemoteAddr();
    }
}

// Зарегистрируем собственный HandlerMethodArgumentResolver
@Configuration
@EnableWebMvc
@ComponentScan("com.walking.springmvc")
public class WebConfig implements WebMvcConfigurer {
    private final IpMethodArgumentResolver ipMethodArgumentResolver;

    // ... - Конструктор и другие методы WebConfig

    @Override
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(ipMethodArgumentResolver);
    }
}

// Теперь мы можем использовать собственную аннотацию @Ip для получения IP-адреса клиента в методах контроллеров
@RestController
@RequestMapping("/my/controller")
public class MyController {
    @GetMapping
    public ResponseEntity<?> get(@Ip String ip) {
        // ... - Реализация метода контроллера
    }

    // Кастомные argument resolver'ы доступны также и в @ExceptionHandler-методах - как объявленных
    // внутри контроллеров, так и в @ControllerAdvice
    @ExceptionHandler(RuntimeException.class)
    public ResponseEntity<ProblemDetail> handleRuntimeException(RuntimeException e, @Ip String ip) {
        // ... - Реализация обработчика
    }
}
```

> Непосредственно в собственной практике мне ни разу не приходилось писать `HandlerMethodArgumentResolver` именно для 
> IP-адреса - обычно он если и нужен, то в логике security, а не методов контроллера, и извлекается иными средствами. 
> Однако реализовывать argument resolver'ы под прикладные задачи несколько раз приходилось - под отдельные заголовки 
> или параметры запроса, специфичные в пределах API конкретных продуктов. 

### Регистрация interceptor'а

```java
// Создание MyInterceptor в качестве бина не регистрирует его автоматически, но избавляет от необходимости вручную 
// создавать объект. Здесь это не критично, но при наличии собственных полей, зависящих от DI,
// это предпочтительный вариант
@Component
public class MyInterceptor implements HandlerInterceptor {
    // ... - Переопределение необходимых методов HandlerInterceptor
}

@Configuration
@EnableWebMvc
@ComponentScan("com.walking.springmvc")
public class WebConfig implements WebMvcConfigurer {
    private final MyInterceptor myInterceptor;

    // ... - Конструктор и другие методы WebConfig

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        // Добавляем сам интерцептор
        registry.addInterceptor(myInterceptor)
            // Указываем, по каким путям (паттернам путей) он доступен. Если не указано - будет применяться ко 
            // всем эндпоинтам в рамках DispatcherServlet, в котором зарегистрирован WebConfig
            .addPathPatterns("/my/controller/1", "/my/controller/2", "/my/controller/new/**");
    }
}
```

`InterceptorRegistry` нам, фактически, необходим только для метода `addInterceptor()`. Однако этот метод возвращает 
объект `InterceptorRegistration`, методы которого стоит рассмотреть чуть детальнее:

- `addPathPatterns()`. Позволяет указать пути запросов, к которым должен применяться перехватчик. Фактически - white 
  list. Метод перегружен, можно указывать пути как через массив (varargs), так и списком;
- `excludePathPatterns()`. Позволяет указывать список путей, к которым перехватчик НЕ должен быть применен - black 
  list. Аналогично предыдущему методу, есть опция передавать параметры как varargs или через список;
- `pathMatcher()`. Позволяет задать собственные правила интерпретации шаблонов. Фактически не используется;
- `order()`. Позволяет указать порядок перехватчика.

Все указанные методы не обязательны для использования.
